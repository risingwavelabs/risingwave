# Main versus serde_bytes: SST metadata CPU and allocations

2026-11-01, Apple ARM64, main `a5a57ad283851a2d177f398f263c47cc00dbb903`
versus serde_bytes fix `5cf5dfde307fbb4f423e380744f842a416d24324`.
Both include the existing block-key reuse optimization. The active production
code differs only in four serde_bytes field annotations; the same bench and
dependency lockfile were used for both libraries.

## Measurements

Values are medians of seven batch means, 64 decodes per batch, after eight warmups.
AB/BA order alternates by batch. The decode includes XXHash64, the actual Foyer
`Box<Sstable>` Code decoder/filter reconstruction, and the cache key; final output
drop is excluded from timings. CPU uses the calling thread's
`CLOCK_THREAD_CPUTIME_ID`, not process CPU divided by an operation count.

| Generated entry | Wall ms, main → fix | Thread CPU ms, main → fix | CPU reduction |
| --- | ---: | ---: | ---: |
| 2.68 MiB, filter-heavy | 8.904 → 2.674 | 8.824 → 2.663 | 69.8% |
| 3.17 MiB, filter-heavy | 10.512 → 3.186 | 10.430 → 3.173 | 69.6% |
| 3.46 MiB, long keys | 8.526 → 0.698 | 8.446 → 0.695 | 91.8% |

Allocation statistics come from **separate instrumented binaries**, with no
allocation-counter TLS in either timing binary. They count requested Rust bytes
on the measuring thread, excluding inputs/setup/printing/other threads. Drop is
inside the allocation scope and must return live bytes to zero for every entry.
All seven batches produced identical allocation statistics for each variant/sample.

| Entry | Allocation calls, main → fix | Reallocs | Requested MiB | Peak live MiB | Returned live MiB |
| --- | ---: | ---: | ---: | ---: | ---: |
| 2.68 MiB | 1,126 → 1,124 | 2 → 0 | 9.6970 → 5.3197 | 6.6969 → 5.3195 | 2.6970 → 2.6970 |
| 3.17 MiB | 1,328 → 1,326 | 2 → 0 | 10.1872 → 6.2866 | 7.1870 → 6.2864 | 3.1872 → 3.1872 |
| 3.46 MiB | 1,538 → 1,538 | 0 → 0 | 3.9210 → 3.9210 | 3.9208 → 3.9208 | 3.4880 → 3.4880 |

The large CPU improvement occurs despite only two fewer allocations, or unchanged
allocation counts for long keys. The dominant benefit is bypassing per-byte serde
visits. Removing two growth reallocations also lowers requested-byte traffic by
45%/38% and peak requested live bytes by 21%/13% for the filter-heavy entries.
The returned entry's live bytes and serialized size are unchanged; this does not
directly reduce the disk-cache logical read-throughput quota.

## Workload, preflight and configuration

The three complete SST files were originally generated by the actual Hummock
builder at deployed revision `4be69f8`, then reused without modification. Each
main/PR binary decodes the native footer, verifies positive filter lookups and
actual SST serde/filter round-trip, and checks identical full meta-cache bytes.
The registered bench can also generate fresh SSTs with main's actual builder.

| Fixture | SST bytes | Meta-cache bytes | Filter bytes | Block-key bytes | Blocks |
| --- | ---: | ---: | ---: | ---: | ---: |
| short_1100k | 39,363,746 | 2,808,372 | 2,750,008 | 42,484 | 559 |
| short_1300k | 46,520,544 | 3,318,821 | 3,249,953 | 50,160 | 660 |
| long_160k | 52,540,972 | 3,630,477 | 454,009 | 3,146,728 | 766 |

The inputs contain 1.1M/1.3M 64-byte keys or 160K 4096-byte keys, 16-byte values,
64 KiB blocks and blocked XOR16 filters. These are generated workloads, not customer SSTs.

Pinned `nightly-2026-06-21` (rustc 1.98.0-nightly `8b6558a02`, LLVM 22.1.7),
release opt-level 3, LTO off, debug 0, incremental off; System allocator.
Dependencies: Foyer 0.22.6, bincode 1.3.3, serde 1.0.228, xorf 0.13.0.
Both host compiler work and the separate Linux Foyer experiment were stopped
throughout the formal window, **10:28:38–10:29:16 UTC**. Twenty-eight child runs
produced 84 CSV rows (5,376 measured decodes). Each child was reaped with `wait4`.

Preflight passed in all four binaries: current-thread CPU clock, real metadata and
filter checks, byte equality, allocator thread isolation, realloc accounting and
zero live bytes after drop. Symbol inspection found no counter TLS in timing
binaries and three counter TLS symbols in allocation binaries. Full workspace
Clippy and explicit bench-feature Clippy passed before measurement.

## Evidence and limits

`target/sstable-meta-main-ab/` contains `raw.csv`, 28 per-batch `.record.txt` files,
per-child stdout/stderr, `measure.json` (including process CPU/RSS/faults/context
switches), `build.json`, source/runner/lockfile/compiler snapshots, all four
binaries, fixture hashes and `summary.md`. Process RSS includes fixture setup:
169.8–178.1 MiB across runs; it is not used as per-entry allocation memory.

Measured harness SHA256:
`d1ade96ddee007f2059b36cffb2c847155ed54dae39cbdec2c0935c07a2b5ffd`.
The per-binary and six fixture fingerprints are recorded in the JSON evidence.
No raw binaries or large SST fixtures are committed.

Requested bytes sum successful allocation/reallocation sizes, counting the new
requested size for realloc. Peak live bytes resize that tracked allocation; they
do not include allocator-internal transient copies, malloc arenas, allocations
bypassing Rust, or the pre-existing input buffer. Returned live bytes are sampled
after decode and before final drop. See [measurement definitions](README.md).

Warm local CPU timings do not include cache lookup, Linux page cache, EBS, async
scheduling or admission; they do not predict production EC2 absolute latency.
Counter-pass timings are deliberately unused. Both production source versions
were restored to the PR source after builds; all benchmark/compiler processes
exited. The PR's production change is separately reviewable in its first commit.
