Range / Blockwise / IO scheduler 四组对照（2026-11-17）

结论

1. 当前连续 Locality 扫描不需要先拆成 block 再依靠 plug 拼回去。本次真实 Locality→HashJoin 路径中，原 Range 的 GET 稳定少于 Blockwise + scheduler；给 Range 加完整 scheduler 几乎没有进一步减少整条链路的 GET。
2. 不能据此删除所有 Blockwise 预读。冷热交错时，它有显著的并发预读收益；补充对照证明该收益在关闭 scheduler 后仍然存在，并非物理合并的收益。
3. scheduler 确实能减少已经提交的相邻/重叠请求：全冷 Blockwise 的 16 个 GET 可以合成约 1 个；Range 与同块点读也可以在派发前合并。但前者对于已知连续扫描是重建 Range 已有的能力，后者是有条件的边际收益。
4. 本次没有证明 admission/runtime dispatch 提升真实链路性能，也未覆盖后端过载、带宽争用或公平调度场景。没有证据支持现在为攒批继续增加复杂逻辑；也没有足够证据据此直接删除所有调度功能。

小测解释

- cold16：Range 三组在 0/2 ms 都稳定 1 GET；D 中位数也是 1，但 0 ms 最多 4、2 ms 最多 2。独立小窗容易凑齐，不代表受 exchange/算子背压影响的实际扫描也同样稳定。
- 单冷读/单独点读没有可合并候选。0 ms 后端时独立点读 p50 A 约 33 us、B 58 us、C 63 us、D 58 us，增加调度/任务切换存在可见成本。2 ms 后端为 3.71/3.78/3.86/3.84 ms；注入 sleep 的实际完成时间还包含 Tokio 定时器粒度与 OS 调度，不是精确 2 ms 的网络模型。
- mixed（扫描与另一 SST 点读）2 ms 时点读 p50 A/B/C/D 为 3.51/3.58/3.61/3.66 ms，p95 为 3.55/3.66/3.75/3.90 ms。本轮未显示 scheduler 的点读延迟优势。各 40 个样本的尾部只作局部观察，不作生产 SLA。
- shared（扫描初始化首次 poll 后点读窗口内第 7 块）：Range A/B 2 GET、68,734 bytes；C/D 在 2 ms 时 GET 中位数 1、64,682 bytes，但均存在拆分样本。启动点与真实 iterator poll 绑定，不依赖 Blockwise 注册计数，不延迟生产代码。
- existing_point（第 7 块点读已开始后再扫描）：Range 2 GET、68,734 bytes；D 通常 3 GET、64,682 bytes。Foyer 共享中间块后，剩下两段不能在 zero-gap 下跨过这个洞；少读一个 block 的字节，未必少一个 GET。这是设计取舍，不是缺失数据或共享失效。
- warm_gaps（交替冷热，8 个冷块）：均为 8 GET、32,222 bytes；2 ms 时 A/B/C 扫描约 37.4/37.4/38.3 ms，D 8.45 ms。原 Range 的缓存启发式在下一个热块处截断，多个冷段逐次读取；Blockwise 提前提交冷块，收益是并发而非合并。
- stop_last：逻辑上 32 块，读到第 16 块第一行停止。四组都只读取 64,682 bytes，没有提前读下一窗；保持现有有限窗口边界。

建议的最小方向

- 连续、已知范围的 Locality 扫描以原 Range 为基线，不继续用 timer 或更多 plug 状态弥补拆窗。
- Blockwise 保留为需要逐块缓存共享、稀疏冷块并发预读的可选能力；本次证明的是场景差异，还没有提出/实现自动策略切换。
- 不额外等待未来的串行 Join probe。当前 scheduler 的有条件合并收益与 admission/runtime 的必要性分开评估；此轮不支持为连续 Locality 路径保留复杂攒批。
- 若准备缩减 scheduler，先明确是否真的需要跨 caller 的物理 IO 并发上限，再决定薄 dispatch 的职责。B 仍有完整队列成本，不能把它的性能等同于尚未实现的简化层。
